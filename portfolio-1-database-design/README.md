# Portfolio 1: Database Design and Modelling (Copay)

**Case study:** Copay, a Nigerian peer to peer lending platform (see the [root README](../README.md) for the full statement and business rules).

## What is in this folder

| File | Purpose |
|---|---|

## Requirements and assumptions

- Between 600 and 3,200 users. The generator default is 3,200 and `--users 600` produces the small version.
- Currency is NGN only. Amounts are `NUMERIC(14,2)`.
- A borrower posts a request with an amount, purpose, tenor in weeks and a flat total interest percentage. Several lenders may fund one request. When fully funded it becomes a loan, the platform takes a 1.5 percent service fee at disbursement, and the borrower repays weekly instalments.
- Deletes are soft (`deleted_at`, status) for users and bank accounts. The ledger is never deleted.

## Design decisions and why

| Decision | Reason |
|---|---|
| `bigint` identity keys instead of UUID | Smaller (8 bytes against 16), ordered inserts keep B-tree indexes compact, and joins are faster. UUIDs would help only if ids had to be created outside the database or hidden from users. `GENERATED BY DEFAULT` lets the seed load explicit ids while keeping foreign keys intact. |
| Double entry ledger (`ledger_transactions` + `ledger_entries`) | Money is never created or destroyed. Each transaction is a set of signed legs that must sum to zero, so every movement has a source and a destination. This is how real payment systems are audited. |
| System wallets (EXTERNAL, ESCROW, FEES) | Give the other side to every entry. EXTERNAL is the only wallet allowed a negative balance, because it represents money held at the banks. |
| `wallets.balance` cached and trigger maintained | Fast reads and a CHECK constraint for "never below zero". Safe because the ledger is append only and `wallet_reconciliation` can prove the cache. See [normalisation.md](normalisation.md). |
| Native ENUM types | Self documenting, small, and invalid statuses cannot be stored. The trade off is that adding a value needs `ALTER TYPE`, acceptable for stable business states. |
| Rules in triggers and constraints, not only in the app | The rules hold for every client: the mobile app, an admin tool, a back office script or a hurried manual fix. |
| Funding trigger locks the loan request row (`FOR UPDATE`) | Concurrent lenders queue on that row, so the funded total cannot exceed the amount. This is used again in Portfolio 3. |
| Idempotency keys on fundings, repayments and ledger transactions | A retried request cannot post twice (Portfolio 3, scenario 6). |
| No performance indexes yet | Only indexes needed for integrity exist (primary keys, unique constraints, `ledger_entries.txn_id` for the balancing trigger). Portfolio 2 measures queries before and after adding indexes, which only works if they start missing. |

## Business rule to mechanism map

| Rule | Mechanism |
|---|---|
| Balance never below zero | `wallets_balance_non_negative` CHECK, fed by the ledger trigger |
| Double entry sums to zero | Deferred constraint trigger `ledger_entries_balanced` |
| Wallet balance equals ledger sum | `ledger_entries_apply_balance` trigger and `wallet_reconciliation` view |
| Funded only up to the amount; FUNDED only when full | `loan_fundings_before_insert` trigger and CHECK constraints on `loan_requests` |
| Cannot lend to own request | Same funding trigger |
| KYC needed above NGN 100,000 | `copay_kyc_limit()` used by the request and funding triggers |
| Oldest instalment first | `repayments_before_insert` trigger |
| No floats for money, NGN only | `NUMERIC(14,2)` and `currency = 'NGN'` CHECK |
| Ledger append only | `BEFORE UPDATE OR DELETE` and `BEFORE TRUNCATE` triggers |

## How to run

See [docs/SETUP_WINDOWS.md](../docs/SETUP_WINDOWS.md) for the PostgreSQL and Python setup. Then, from the repository root:

```powershell
python portfolio-1-database-design\seed\generate_seed.py --reset
psql -f portfolio-1-database-design\rule_tests.sql
```

Use `--users 600` for the small version. The same `--seed` always produces the same data. `--reset` drops and recreates the `public` schema, so it destroys existing data.

The seed script prints its own row counts and runs the reconciliation checks. Typical output ends with:

```
Reconciliation: wallets where cached balance <> ledger sum = 0
Ledger grand total (must be 0.00) = 0.00
```

### How the generator works

It runs a time ordered event simulation (a priority queue of events) instead of inserting random rows. Events are request creation, lender funding, disbursement, instalment repayment and withdrawal. A balance check happens before each event, and a wallet is topped up from EXTERNAL if it is short, exactly as a real user would fund a wallet first. Because events are processed in time order, every wallet balance stays valid at every point in history. The data is then bulk loaded with `COPY` in dependency order and the database triggers validate every row again, so the generator and the database independently agree.

Names are drawn from curated lists of common Nigerian names for realism. Faker is used in Portfolio 4 for the free form application payloads.
